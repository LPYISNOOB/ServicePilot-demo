# ServicePilot 参数调试指南

本文专门说明哪些参数可以改、改了会发生什么、需要重启还是重建数据，以及应该用什么测试证明没有破坏安全规则。

## 1. 参数分为三层

| 层 | 文件/位置 | 适合内容 | 是否含秘密 |
|---|---|---|---|
| 业务规则 | `config/business_rules.json` | 阈值、风险词、RAG K、合成数据规模 | 否 |
| 运行环境 | `.env` | 模型接口、端口、数据库路径、LangSmith | 可能含 API Key |
| 政策内容 | `data/policies/*.md` | 退款、物流、质保等企业制度 | 否，但真实企业可能敏感 |

不要把 API Key 放进 `business_rules.json`、React `.env` 或 Git。

## 2. 审批规则

配置：

```json
"approval": {
  "refund_amount_threshold": 200.0,
  "require_all_business_writes": true,
  "require_all_compensation": true,
  "require_high_risk_review": true
}
```

| 参数 | 默认 | 作用 | 推荐范围 |
|---|---:|---|---|
| `refund_amount_threshold` | 200 | 超过该金额时增加高金额审批原因 | 100—1000，按企业制度 |
| `require_all_business_writes` | true | 任意退款数据库写入都必须人工审批 | 演示和生产保持 true |
| `require_all_compensation` | true | 优惠券、积分、现金等补偿必须审批 | 保持 true |
| `require_high_risk_review` | true | 法律、安全、监管类风险必须审批 | 保持 true |

注意：把金额阈值改为 500，不代表 299 元退款会自动执行。因为 `require_all_business_writes=true`，它仍需审批；
只是审批原因不再显示“超过 200 元”。如果确实想演示低金额自动退款，需要同时把 `require_all_business_writes=false`，
但这会降低安全性，修改后必须新增测试。

建议测试：

```powershell
python -m pytest tests/test_workflow.py
python -m servicepilot.evaluation
```

## 3. 风险词与中风险意图

```json
"risk": {
  "high_keywords": ["律师", "起诉", "监管", "消协", "媒体", "曝光", "人身伤害", "起火", "冒烟", "漏电", "报警"],
  "medium_intents": ["refund", "damaged_goods", "complaint", "warranty"]
}
```

新增高风险词时建议使用具体短语，避免过宽。例如单独加入“火”会误伤“火速处理”。可以加入：

- `爆炸`
- `电池鼓包`
- `召回`
- `集体投诉`
- `新闻记者`

改完要在 `evals/cases.jsonl` 增加正例和反例，至少包括：

- 应该命中 high 的句子；
- 包含相似词但不应命中的句子；
- 同时含退款和安全问题的句子。

## 4. RAG 参数

```json
"retrieval": {
  "top_k": 3,
  "minimum_score": 0.0,
  "active_documents_only": true
}
```

| 参数 | 默认 | 影响 |
|---|---:|---|
| `top_k` | 3 | 返回给回复 Agent 的证据数量；越大上下文越多，也越容易混入噪声 |
| `minimum_score` | 0.0 | 丢弃低相似度文档；本地哈希分数不应直接套用其他 Embedding 的阈值 |
| `active_documents_only` | true | 预留参数；当前实现始终执行 active/effective-date/region 安全过滤 |

调试步骤：

1. 先运行 `python -m servicepilot.evaluation` 保存基线；
2. 只改一个参数；
3. 重新启动 API；
4. 对比 `evidence_recall_at_3` 与误召回；
5. 抽查回复引用是否来自当前版本。

不要为了让固定 50 条样本达到 100% 而无限添加意图提示词，这会造成测试集过拟合。应新增措辞变化和无关问题。

## 5. 合成数据规模

```json
"demo_data": {
  "random_seed": 42,
  "customer_count": 100,
  "order_count": 500
}
```

修改后，已有数据库不会自动覆盖。需要执行：

```powershell
python -m servicepilot.seed --force
```

`--force` 会清除演示工单、退款和审计记录，只能对本项目合成数据库使用。

保留 `random_seed=42` 可以让数据、测试和演示可复现。做性能实验时可以增到 10,000 客户和 100,000 订单，
但 SQLite 和当前同步 API 不代表真实生产吞吐。

## 6. 模型参数

`.env`：

```dotenv
SERVICEPILOT_MODEL_MODE=openai_compatible
SERVICEPILOT_MODEL_NAME=your-model-name
SERVICEPILOT_API_KEY=your-secret
SERVICEPILOT_BASE_URL=https://provider.example/v1
SERVICEPILOT_TEMPERATURE=0.1
```

| 参数 | 建议 | 原因 |
|---|---|---|
| 模型 | 支持 structured output 的小型指令模型 | 分类稳定、成本低 |
| temperature | 0—0.2 | 客服与分类更看重一致性 |
| timeout | 代码中 45 秒 | 防止服务长时间占用连接 |
| max retries | 代码中 2 | 避免瞬时失败，也避免无限重试 |

更换模型后必须重新评测。Mock 的 100% 不代表真实模型也是 100%。真实模型可能输出 Schema 不兼容、过度解释或引入事实。

## 7. 数据库和 checkpoint

```dotenv
SERVICEPILOT_DB_PATH=D:\ServicePilot\data\servicepilot.db
SERVICEPILOT_CHECKPOINT_PATH=D:\ServicePilot\data\checkpoints.db
SERVICEPILOT_CHECKPOINT_MODE=sqlite
```

- 业务 DB 保存客户、订单、工单、退款和审计；
- checkpoint DB 保存 LangGraph 线程状态；
- 两者必须分开，便于权限、备份和迁移；
- `checkpoint_mode=memory` 只适合一次性单元测试，服务重启会丢失待审批任务。

如果切换路径，确保目录可写，并让恢复请求连接同一个 checkpoint 文件。

## 8. FastAPI 与 CORS

```dotenv
SERVICEPILOT_HOST=127.0.0.1
SERVICEPILOT_PORT=8000
SERVICEPILOT_CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

开发时允许本地 Vite。生产中不要使用 `*` 并同时开启 credentials；应只允许正式前端域名。

如需局域网演示，可以临时把 host 改为 `0.0.0.0`，同时检查 Windows 防火墙。不要直接把没有认证的审批接口暴露到公网。

## 9. LangSmith

```dotenv
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=your-key
LANGSMITH_PROJECT=servicepilot-demo
```

ServicePilot 已给图调用附加 `servicepilot`、`supervisor-multi-agent` 和 `human-in-the-loop` tags，
并在初始运行 metadata 中写入 ticket_id。不开启 LangSmith 时，项目不受影响。

注意：真实企业数据进入第三方可观测平台前，需要完成数据出境、脱敏和供应商安全评审。

## 10. 政策文档参数

新增政策文件时必须提供：

```yaml
id: 全局唯一 ID
title: 人类可读标题
version: 版本
effective_date: YYYY-MM-DD
status: active 或 inactive
region: ALL 或区域
risk_level: low/medium/high
tags: 逗号分隔关键词
```

版本升级建议：

1. 复制旧文件创建 V2；
2. 新文件设 `active` 和新生效日期；
3. 旧文件改为 `inactive`，不要删除，以便审计；
4. 增加检索测试，确认 V2 命中且 V1 不命中；
5. 重启服务。

## 11. 安全调参红线

以下改动不能只看 UI“能跑”就接受：

- 关闭所有业务写入审批；
- 让 LLM 直接生成并执行 SQL；
- 取消订单归属验证；
- 允许 inactive 或未来政策参与回复；
- 在 React 中配置 API Key；
- 删除审批审计；
- 把高风险规则完全交给 Prompt。

每次修改安全规则，都应同时修改测试与评测，保存改前和改后的报告。
