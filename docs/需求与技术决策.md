## 3. ADR-001：程序化 Supervisor

状态：接受。

业务关键路径固定，使用 `Command(goto)` 保证顺序。LLM Supervisor 的灵活性不足以抵消跳过风控、难测试和额外成本。

## 4. ADR-002：专业 Agent 不等于全部使用 ReAct

状态：接受。

Intent/Response 使用模型，Order/Policy/Risk/Action 主要使用工具与规则。Agent 的定义是独立职责、状态输出和权限边界，
不是必须无限工具循环。这个选择更适合企业流程。

## 5. ADR-003：本地优先

状态：接受。

使用 SQLite、Markdown、哈希 Embedding 和 Mock，解决没有数据库、没有真实文档、没有 API Key 的限制。
接口保留生产替换点。

## 6. ADR-004：所有写入人工审批

状态：接受。

退款金额阈值用于增加风险提示，但默认任意退款写入都审批。避免“小额自动执行”在学习项目中掩盖资金风险。

## 7. ADR-005：双数据库文件

状态：接受。

业务数据与 LangGraph checkpoint 分离。前者属于领域模型，后者属于编排运行时，备份、权限和迁移方式不同。

## 8. ADR-006：单容器交付

状态：接受。

Docker 多阶段构建 React，再由 FastAPI 托管静态文件。适合作品集和 PoC；生产可拆分 CDN 与 API。

## 9. 明确不做

当前阶段不加入：

- Kafka；
- Kubernetes；
- Neo4j；
- Milvus；
- Redis 集群；
- 真实支付；
- 微服务拆分。

原因不是这些技术没价值，而是当前数据量和业务闭环不需要。过早增加会稀释 Agent、HITL、评测和交付能力。
