# ServicePilot 简历与面试指南

## 1. 项目标题

推荐：

> ServicePilot｜基于 LangGraph 的企业售后多智能体与人工审批平台

避免只写“智能客服机器人”，因为项目真正有区分度的是可恢复工作流、业务工具、安全边界和评测。

## 2. 简历项目描述

可直接改写，但不要把合成数据写成真实生产流量：

> 独立设计并实现电商售后多智能体平台，使用 LangGraph Supervisor 编排 8 个专业 Agent，打通订单核验、版本化政策 RAG、退款方案、风险规则、Human-in-the-loop 审批、业务写入、审计与回复；基于 FastAPI + React 交付可演示控制台，使用 SQLite checkpoint 支持待审批任务跨服务实例恢复，并构建 50 条合成回归评测与 Docker/CI 流程。

量化 bullet：

- 设计 8 Agent 共享状态工作流，将 LLM 语言任务与确定性资金/隐私规则分离，确保退款写操作在人工审批前不执行。
- 构建含版本、生效日期、区域和来源的政策 RAG；在 50 条固定合成用例上实现 Intent、审批路由、隐私错误和 Evidence Recall@3 均 100%，并明确该结果不代表生产准确率。
- 使用参数化 SQLite、订单归属联合查询和事务审计，覆盖错误邮箱越权、inactive 政策、审批拒绝零写入、服务重建后恢复等 12 项自动测试。
- 以 FastAPI + React/TypeScript 完成交互式审批和 Agent 轨迹面板，提供 Mock/OpenAI 兼容模型切换、多阶段 Dockerfile 与 GitHub Actions。

## 3. 针对不同岗位的讲法

### AI 应用工程师

重点：端到端交付。

- 模型边界如何接 OpenAI 兼容服务；
- RAG 数据如何组织；
- FastAPI/React 如何承载；
- Mock 模式如何降低开发成本；
- 测试、Docker、CI 如何保证可交付。

一句话：我不仅写 Prompt，还把 Agent 变成可安装、可测试、可展示的完整应用。

### Agent 工程师

重点：状态、编排和副作用。

- 为什么是 Supervisor + bounded agents；
- `Command(goto)` 如何路由；
- `interrupt` 与 `Command(resume)` 的语义；
- checkpoint 如何跨实例恢复；
- 为什么副作用放在审批之后；
- trajectory 如何评测。

一句话：我把多 Agent 当作有状态分布式工作流设计，而不是多个 Prompt 串联。

### AI 产品经理

重点：业务闭环和指标。

- 用户：客户、客服、审批经理；
- 价值：减少查单/查政策时间，控制错误退款；
- 风险：隐私、错误承诺、过期政策、审批容量；
- 指标：自动解决率、接管率、准确率、退款风险、P95、成本；
- 灰度：先建议模式，再低风险自动化。

一句话：我把模型能力转成可审批、可审计、可评估的业务流程。

### FDE

重点：客户现场适配。

- 用合成数据快速做 PoC；
- 通过 Repository、LanguageService、PolicyRetriever 隔离客户系统差异；
- 参数文件允许现场调整阈值和风险词；
- 明确从 SQLite 到 Postgres、从 Mock 到客户模型、从模拟退款到支付 API 的迁移路径；
- 用验证脚本快速判断环境问题还是代码问题。

一句话：我能在缺数据库、缺文档、供应商不确定的环境下先交付闭环，再逐步接入客户系统。

## 5. STAR 讲述模板

### Situation

企业售后既需要模型理解自然语言，又涉及订单隐私和资金操作，单一 ReAct Agent 难以保证流程顺序和权限边界。

### Task

在没有真实数据库和企业文档的情况下，做出可本地运行、可审批、可审计和可量化评测的完整 PoC。

### Action

- 生成固定种子的合成业务数据和版本化政策；
- 用 Supervisor 编排 8 个专业 Agent；
- 用确定性风险规则阻止模型绕过审批；
- 用 SQLite checkpoint 实现恢复；
- 用 FastAPI/React 交付控制台；
- 建立测试与 50 条评测。

### Result

本地完成端到端退款暂停/恢复，12 项测试通过，固定 50 条合成用例全部通过，前端生产构建成功；并形成生产迁移清单。

## 6. 高频面试问题

### 为什么不直接用一个 ReAct Agent？

因为订单查询、政策检索、资金审批和写入有不同权限。分 Agent 后可以最小授权、独立测试和明确审计；Supervisor 保证必经顺序。

### 这是真正的多 Agent 吗？

是职责、状态和工具边界独立的 specialist agents，由 Supervisor 调度。不是每个 Agent 都必须拥有一个自由 ReAct 循环；
业务流程 Agent 使用确定性执行往往更可靠。Intent/Response 可使用 LLM，Order/Risk/Action 主要使用工具与规则。

### 为什么 Supervisor 不是 LLM？

售后主路径是确定业务流程。程序化 Supervisor 可证明审批不会被跳过，延迟和 Token 更低。未来可让 LLM 选择非关键技能，但安全节点仍强制执行。

### Prompt Injection 怎么防？

不依赖“请忽略恶意指令”这一句 Prompt。LLM 不拿任意 SQL、代码执行或支付权限；动作必须是白名单结构，风险由代码判断，业务写入需要人工审批。

### RAG 为什么不用向量数据库？

当前只有 8 份短政策，InMemoryVectorStore 足够且零运维。关键是先实现版本治理、引用和评测。规模上升后接口可替换 pgvector/Milvus。

### SQLite 能企业上线吗？

不能支持高并发多副本生产，但适合本地 PoC。项目明确把业务 Repository 和 checkpoint 隔离，生产路线是 Postgres + Postgres checkpointer。

### 100% 准确率可信吗？

它只说明固定的 50 条合成回归集在 Mock 规则下通过，不是生产泛化率。我会扩展盲测、真实模型、对抗样本和人工标注，并报告置信区间与数据分布。

### 如何避免重复退款？

当前演示用人工审批和事务降低风险，但真实集成还需要幂等键、支付网关 request ID、唯一约束、outbox 和重试语义。这是生产化清单中的高优先级项。

## 7. 不要夸大的内容

不要写：

- “服务百万用户”；
- “生产准确率 100%”；
- “已接入真实支付系统”；
- “实现企业级高可用”；
- “所有代码完全原创”而不提官方项目启发。

可以写：

- “作品集级/production-shaped MVP”；
- “合成 50 条固定评测集”；
- “提供生产迁移设计”；
- “参考 LangChain 官方生命周期项目并重新实现中文业务与安全层”。

这种诚实反而能体现工程判断。
